# Decisions Log

Decisions made autonomously while the owner was away. Each can be revisited.

- **D-001 Stack**: TypeScript + Vite + three.js (WebGL2) + React for UI overlays. WebGL2 over WebGPU for laptop/browser compatibility.
- **D-002 Original IP**: All parts, art, names original. Agency name in-game: "Web Space Program". Crew are humans ("astronauts"), not a mascot species.
- **D-003 Scale**: Real data is the source; `s` scales lengths, GM by s² (preserves surface gravity), the atmosphere profile is compressed vertically by s^0.3 (standard → Earth atmosphere ≈ 70 km, like the genre classic), rotation periods by s^0.5. Default preset `standard` s=0.1. `real` preset uses exponent 1 for everything.
- **D-004 Rigid vessels**: Vessels are single rigid bodies (no wobbly joints). Structural failure via load thresholds. Removes KSP's "Kraken" class of bugs.
- **D-005 Gravity**: Patched conics for prediction and on-rails; physics mode uses dominant-body gravity, with optional n-body perturbations later.
- **D-006 Launch site**: Cape Canaveral-ish latitude (28.5°N) on Earth, east coast. Named "Coastal Launch Complex".
- **D-007 Autopilot building blocks** (`src/game/autopilot.ts`): planners (circularize, transfer to child/parent body, course correction) add maneuver nodes; controllers (ascent, node execution, powered landing) return a `ControlInput` per frame plus an optional `coastUntil` UT so any driver (tests now, an in-game autopilot later) can rails-warp idle phases. Node burns track remaining dv from measured proper acceleration and, for prograde/retrograde burns, stop on the planned orbital energy (finite-burn losses otherwise wreck near-escape burns like TLI). Landing = predictive suicide burn + slope-aware terminal descent (diverts to ground under ~8°). `tests/world-moon.test.ts` flies the stock Selene lander Earth → Moon landing → back into Earth's SOI with no balance changes.
- **D-008 Terrain relief**: relief scales by s^0.8 (standard: 0.16×) — slightly exaggerated vs radii for drama, but lunar slopes stay landable.
- **D-009 Tracking Station warp**: tracking uses the existing active-vessel warp clamps and encounter stops through `World.tick`; fleet focus is independent of the simulation's active vessel. With no active vessel, `advanceRailsTo` packs and propagates unattended vessels using existing rails event rules. Fleet conics refresh at 2 Hz while icon positions and floating-origin transforms update every frame.
- **D-010 Interplanetary targeting**: `src/game/interplanetary.ts` searches a scaled-ephemeris Lambert departure/flight-time grid, minimizes estimated ejection plus circular capture cost (capture optional), resolves the actual parking-orbit ejection plane and phase, and refines time/prograde/normal/radial against Earth → Sun → target patched conics. Prograde transfers with no complete extra revolutions only; exactly collinear Lambert endpoints are rejected as plane-ambiguous. Moon departure requires first reaching a planetary parking orbit. Ringrunner uses existing chemical engines and tanks, with no part balance changes; small late cruise trims are required because finite burns leave sub-m/s errors that matter over years. `porkchopGrid` exposes pure data for future UI work. The synchronous planner currently takes a few seconds; a worker is deferred.
- **D-011 Crew / EVA**: Crew are original human astronauts, generated from a persisted integer seed. Roster IDs live on command `PartState`s so staging and docking UID remaps preserve assignments. Catalog pod dry mass includes occupied seats (100 kg per suited astronaut); empty seats subtract that mass, preserving stock launch balance. EVA uses a runtime-only `eva-astronaut` part (95 kg dry + 5 kg monopropellant) and a dedicated DOM-free character step in the existing vessel/rails system. Hatch transfer preserves combined COM and linear momentum, with no separation impulse. Ground speed is 1.4 m/s walking / 3.5 m/s running, hop 2.5 m/s, slope limit 45°. Jetpack thrust is 35 N with 600 m/s exhaust velocity (~30.8 m/s total Δv). Boarding within 3 m of a free hatch and below 3 m/s relative speed services/refills the suit from abstract cabin supplies. Enter boards, leaving B available for aircraft brakes. Flags are body-fixed surface objects. Empty pods without a probe core accept no flight control or staging. Saves without crew data receive deterministic launch-style assignments on load.
- **D-012 Aircraft**: jets are `EngineModule`s with `airBreathing` (thrust = static thrust × Mach curve × (ρ/1.225)^k × intake-air fraction; fuel-only Isp, liquid fuel only). Intake air is produced every step and never stored (leftovers vented), so starvation at altitude/low speed is immediate; jets flame out below 15 % supply and relight automatically. Wheels are spring/damper suspensions with an impulse tyre model (lateral grip with sticky/sliding μ, rolling resistance, brakes inside a friction circle); steering fades with speed. Editor core now uses the catalogue surface-mount convention (srf node / −Z face); SPH crafts build horizontally (view-only rotation, craft +Y stays the nose) and launch on the runway (`World.launch(craft, 'runway')`, free on their wheels, no clamps).
- **D-013 Science / career**: `World.mode` defaults to `sandbox`; optional `SavedWorld.mode/progression` preserve version-1 saves. The executor's cut-off tail uses `spoolDownTime` (a rocket cut now ends in ~0.1 s), simulated with the engine's own discrete decay.
- **Lost control after assists (owner bug):** the assist could hand back a vessel still packed on rails warp (a "warp to" left running when the program started, or a program ending/failing without owning warp). A packed craft ignores throttle, attitude and SAS until a command or staging drops warp, which is why toggling gimbal lock "fixed" it. `flight/assist.ts assistFrame` now owns warp for the whole program (rails warp only while coasting, 1× on every other frame and at any end), passes the pilot's part commands/RCS/gear/brakes through, and hand-back enables SAS attitude hold. `World.tick` drops rails warp when the pilot steers or throttles a live engine (staging already did). Directional SAS holds yield per axis to pilot input (a saturated hold summed with the input cancelled it); a maneuver hold with no node falls back to attitude hold. `isTyping` no longer counts switches, sliders and buttons as text fields (a focused part-menu switch silenced every flight key); HUD selects blur after a pick. Regression: `tests/assist-handback.test.ts`.
- **Node executor:** turns to the burn at 1× before warping (rails keeps attitude); starts when half the Δv is delivered by the node time, from the per-stage Δv readout plus 1 s per staging; stages whenever nothing can thrust (never below `minStage` or into a parachute stage); steers with Lambert guidance to a quarter-turn aim point on the planned orbit; cuts on the exact planned orbital energy (quadratic, not linearised) with a simulated discrete spool-down tail. One physics step at minimum throttle is ≈0.3 m/s on the Selene booster (≈±25 km at the Moon after a TLI), so the main cut lands a step early and is trimmed with the engines' thrust limiters set temporarily (e.g. 6%); `Autopilot.release()` restores the player's limiter values however the program ends (done, failed, pilot override), and `runAutopilot` applies them too. A finite-burn TLI from the stock Selene orbit scenario (three start times) ends <0.5 m/s from the plan with the lunar periapsis within 6.3 km of planned (energy now exact; the rest is finite-burn direction) (`tests/assist-node.test.ts`; before: no staging until 34 s past the node, periapsis 819 km).
- **Departure options:** `game/planning/windows.ts` scans Lambert departures from the vessel's actual orbit in any plane (moons: one lunar month; returns home: half a month, any return plane and radial speed). The cheapest within the next revolution is the "now" option (usually a plane change); later local minima are windows. `planTransferToBody` takes the earliest option within 8% + 25 m/s of the cheapest (the first-window planner when it qualifies, else a Lambert-seeded patched-conic refinement), returns the options in `TransferPlan.windows`, and `options.departure` plans a specific one. The maneuver planner lists them (wait, Δv, flight time, soonest/cheapest/plane-change tags).
- **Interplanetary:** the grid now scores the real single-burn ejection from the fixed parking plane (min over the revolution) instead of a coplanar departure, which had picked windows needing 2–2.5× the Hohmann Δv from inclined orbits; options over two synodic periods rank departure + capture like the planner.
- **Matrix:** `PLANNER_MATRIX=1 npx vitest run tests/planner-matrix.test.ts` runs 135 requests (three scales; LEO at 0/28.5/51.6/90/140°, MEO, elliptical, part-burnt, overshot; lunar returns; Mars/Venus) and judges Δv against the best achievable single burn, waits against earlier near-equal options, encounter periapsis and the map's prediction.

## Control responsiveness (2026-10-07)

- **D-THROTTLE Rocket throttle response**: liquid rocket engines follow their `spoolTime` only for the start-up transient after ignition (`EngineState.spooledUp`, optional, reset whenever the engine is not ignited). Once running, throttle changes and cuts use `ROCKET_THROTTLE_TIME` = 0.02 s, so a full-throttle cut ends thrust in 0.1 s (previously the spool lag kept thrust for 4.6 × spoolTime, e.g. 4.6 s on the 1.0 s lifter, and Ap kept rising for 2–3 s after the player cut). Jets keep their turbine spool time in both directions; solids are unchanged. The node executor's cutoff anticipation uses `spoolDownTime`. The map path caches (`trajectory()`, `mapTrajectory()`) refresh at once when thrust ends instead of keeping a prediction made under thrust for the 2 s coasting age. Any pilot throttle input (cut/full keys, ramp keys, analog trigger) now cancels a running flight assist, as manual attitude input already did; before, the assist overwrote a throttle cut every frame.
- **D-MAPBURN Map path while burning**: under thrust the map draws the current-SOI conic recomputed from the live state every frame (`World.burnTrajectory`, ~0.1–0.4 ms) plus only the next continuation; `trajectory()` computes just those two patches while thrusting (5 Hz). Deeper continuations (re-encounters after a lunar escape and the like) change branch with every m/s and flickered between refreshes; they return within one frame of the engines stopping. A cached continuation whose start no longer matches the live conic's end (e.g. the escape just closed) is dropped until the next refresh. `MapView` rebuilds only the lines whose patch changed. Precise-gravity (numerical) map paths are unchanged. Probe: `scripts/map-burn-probe.ts`.
- **D-HUBLOAD Space Center first load**: the hub scene compiles its programs in slices (as flight does), updates without drawing until then, and keeps its canvas transparent behind a "Preparing the launch complex…" label until Earth's surface is ready (12 s cap), then fades in over 0.45 s. `PlanetRenderer.surfaceReady` no longer reports ready while the untextured far sphere stands in for wanted near terrain (also tightens the flight loading gate). Cold new-career load on the RTX harness: before, content from ~2.5 s after Start with ~1.5 s of white ground and pop-in, settled ~5 s; after, nothing until a single fade-in at ~4–4.5 s on the settled scene.

## GPU pass 2 (2026-10-07, cx/perfgpu2)

- **Aerial integration follows density variation on Low/Medium.** Short, nearly level daylight rays use one or two integration segments when their radial span, including chord sag, is small relative to the aerosol scale height. Exponential segment integration is exact for constant density; this is an approximation when density varies. Sunset/night, long horizon rays, optically thick step multipliers, High and Ultra keep the original budget. Airless bodies return before atmospheric ray calculations. Geometry, imagery, terrain and ocean fragment shading are unchanged. Paired measurements and visual comparisons are recorded in `docs/PERFORMANCE.md`.
- **Only certainly hidden Earth sky rays are discarded.** Logarithmic fragment depth prevents ordinary early depth rejection from avoiding the sky march. A CPU Float64 bound places an occluding sphere below the global terrain minimum, triangle sag and a precision margin. Rays through that sphere cannot show sky behind the complete opaque Earth surface, including launch-trench floors. Apply the shortcut only within two Earth radii: distant Float32 ray discriminants lose precision, and those small discs provide little benefit. The horizon band retains the original shader. Other bodies retain the original sky path.
- **Flight terrain/ocean use reusable batches when multi-draw is available.** Preserve the existing chunk vertices, attributes, per-chunk culling and rebased transforms; combine each material family into a `BatchedMesh`. Reserve GPU slots for the peak selected chunks and reuse them through LOD changes, rather than retaining GPU buffers for the whole terrain cache. Matrices are computed after Float64 floating-origin subtraction before their Float32 texture upload. Low and browsers without `WEBGL_multi_draw` retain ordinary meshes; hub/map/portraits also retain their existing path. This adds a matrix texture fetch and some reserved buffer capacity in exchange for fewer draw submissions. No shader precision reduction is assumed safe without Apple hardware evidence.
- **Medium clouds skip detail noise only at zero baked coverage.** Noise multiplies coverage, so this branch returns the same zero. Evaluate footprint derivatives before branching to preserve cloud-edge filtering. Restrict the shortcut to Medium; High/Ultra keep their original branch structure and Low disables clouds. Three interleaved pad pairs improve 2.530→2.493 ms.
- **Keep equivalent shader expressions without attributing an unproven speedup.** Terrain colour/coverage and GB slope reuse the same triplanar fetches, preserving the original cyclic accumulation order. The positive Mie denominator uses `x * sqrt(x)` for `pow(x, 1.5)` without changing the scattering model. Isolated RTX pad medians are essentially equal (fetch sharing 2.529→2.527 ms; phase rewrite 2.494→2.496 ms). These make the intended reuse/algebra explicit to compilers; Apple performance remains unmeasured. The wider terrain/ocean/shadow math experiment regressed and was removed.
## CPU pass 2 (2026-10-07, cx/perfcpu2)

- Preserve the flight HDR/bloom/AA attachments while the map renders directly to the canvas. Resize them on return only if the flight resolution actually changed. Avoid resetting an unchanged canvas backing store. This retains GPU memory during map view in exchange for removing repeated allocation/upload work when opening and closing it.
- Decode and crop Earth imagery in a lazily created worker; transfer ImageBitmap strips and terminate the worker after 30 idle seconds. The fallback yields between crops. Stream at most four 1 MiB uploads / 1 Mpx merges per frame with a 0.75 ms soft submission budget. Driver allocation and mip generation remain indivisible; actual maxima must be measured, not described as hard guarantees. The bundled surface preview has priority over cloud-source uploads; existing imagery remains visible while higher detail streams. Full imagery takes more frames to arrive.
- Part texture placeholders are one texel, with the same constant colour as before. Adopt the worker's transferred final buffer through the shared three.js Source instead of copying it into an eagerly allocated full-size placeholder. Repeat clones keep their Source and sampler settings. Earth terrain workers receive one immutable Blob (or the existing SharedArrayBuffer) and materialise their local grid off the main thread; initialization waits for the grid before any terrain request.
- Reuse part visuals by PartState identity when a vessel splits, before the donor is rebuilt. Heat slots, plume state and soot move with the hardware; unrelated vessels with matching local UIDs cannot donate. Separation preserves existing soot instead of washing off marks from a departed nozzle. Newly built or repositioned assemblies still bake their layout. This is a render-only trade-off; staging, physics and save data are unchanged.
- Empty part inspector layers do not request animation frames or force layout. Production editor/thumbnail renderers skip synchronous shader info-log queries, matching the existing flight pipeline; development builds retain shader diagnostics. Graphics settings use human-readable labels while persisted values remain unchanged.
- HUD impact prediction only requests a multi-body trajectory after its existing terrain/periapsis/situation test says an impact is possible. A safe orbit or flyby still returns the same null impact, but stops paying 60–70 ms sampled prediction costs in throttled Moon traces. Map paths remain available on demand; the HUD no longer keeps their cache warm incidentally. Suborbital impact searches retain the SOI bound. No simulation or prediction algorithm is changed.
- Transfer last-owned imagery bitmaps back to the same worker for disposal. The first small-strip implementation moved decoding off the main thread but synchronously closed all strips when releasing a level; the continuous ascent trace exposed 80 ms sampled in those closes. A worker can be recreated after idle termination for this cleanup. If workers/transfers are unavailable, close one bitmap per timer task. Only the final decoded-cache reference can relinquish ownership, after submitted GPU copies no longer need the JS bitmap handle.

## CPU pass 2, round 2 (2026-10-08, cx/perfcpu2)

- **Terrain chunk size:** every quality preset doubles `chunkResolution` (Low 48, Medium/High 64, Ultra 96). Selection still splits on each chunk's vertex spacing, so screen error stays at or below the preset target and `maxLevel` drops by one automatically. The pad selects ~200 instead of ~535 chunks: draw calls, not triangles, dominate the frame on the CPU. Triangle count rises modestly, per-chunk worker builds take ~4× longer and the LRU caches were cut to about a quarter so memory stays similar. Revisit with the GPU pass if vertex cost on Apple GPUs turns out to matter more.
- **Static containers:** the flight `Scene`, `PlanetRenderer.root` and the quadtree group are `matrixAutoUpdate = false` (they never move), so their per-frame `updateMatrix()` no longer forces a matrix multiply on every descendant, including hundreds of hidden cached chunks. The flight scene also has `matrixWorldAutoUpdate = false`; the controller calls `scene.updateMatrixWorld()` once per frame before rendering. Anything that transforms one of these containers must call `updateMatrix()` itself.
- **Shadow map cache:** `render/core/shadowCache.ts` sets `shadow.autoUpdate = false` on the sun and requests a redraw only when a visible caster that can reach the light's volume (conservative cylinder test) moved by more than a quarter shadow texel (rotation scaled by the caster's reach), changed geometry/instances, appeared or disappeared, or the light camera or map changed. Pad and attitude-hold orbit skip ~90–95% of depth passes; ascent still redraws every frame.
- **Rigid batching of animated parts:** `batchStaticParts` takes a `skip` predicate; `isAnimatedNode` lists every node flight animates or restyles (gimbal, exhaust anchors, deploy data, gear joints, brace stages, control surfaces, lamp lenses, EVA limbs). Everything else in engines, panels, pods and gear joins the vessel batch. EVA vessels and the stress overlay keep individual meshes. A new animation in `VesselView.animatePart` must add its node name there.
- **Ephemeris:** caches states for four recent times (LRU) instead of one; the frame interleaves physics, interpolated render and world times. Values are unchanged.
- **Terrain selection reuse:** the quadtree reuses the previous selection while the body-fixed camera position (1 cm), orientation (1e-6), projection and chunk set (version bumped on attach/dispose) are unchanged, and then skips eviction.
- **Near-radial conics:** `stateToElements` derives a hyperbola's mean anomaly from the state (e·sinh F = r·v / √(μ|a|)) instead of from ν. On a radial approach ν lies within rounding of an asymptote and the conversion threw, unmounting flight.
- **Autosave persistence:** flight autosaves snapshot (`serializeWorld`) synchronously, then stringify, write the slot index and write the legacy key as three separate idle tasks (`requestIdleCallback`, 1 s timeout). Every save read, other save and `pagehide`/hidden visibility flush the queue first, so ordering and visibility are unchanged; a failed step reports once and skips the rest of that save. Quicksaves and hub/tracking saves stay synchronous. The slot index caches each slot's JSON while storage still holds exactly the text it last wrote, so a write stringifies only the new slot; any outside change (another tab, import) re-parses. Save format and keys are unchanged.
- **Imagery streaming budget:** replaces the fixed 0.75 ms / four-operation budget, which at 4× throttle admitted one 1 MiB unit per frame and tripled stream time. Each frame now spends about 6% of the measured frame interval (1–3 ms), admits a unit only if its predicted cost fits, and starts allocation/mip-generation units only at the beginning of a frame. Worker decoding and 1 MiB strips stay.
- **Not changed, by choice:** packed/prelaunch hazard stepping and stage-Δv readout cadence (both would change simulation or readout results), React HUD memoisation (≈0.4 ms real at a 10 Hz tick, spread thinly) and the navball's separate WebGL context.

- **Maneuver node anchored during its burn (op/mnvexec):** a node's planned orbit used to be re-derived from the live vessel every refresh (`live orbit at node.time + whole node Δv`), so it ran away from the target while burning, and it vanished the moment the node time passed. `ManeuverNode.anchor` (optional, persisted with the node) now freezes the planned post-burn state (body-relative position + velocity at the node time). `game/world/nodeAnchors.ts` keeps a fresh pre-burn plan for the next node (≤ 1 h ahead, every 0.5 s) and promotes it to `node.anchor` on the first engine thrust inside the burn window (`node.time − (burn + 30 s)` … `node.time + 1.5·burn + 60 s`, burn = Δv/(F/m)). Edits to the node (any field, time) or an SOI change invalidate the anchor (`validAnchor`), so editing re-plans from the live orbit as before. `predictTrajectory` continues from the anchored state at the node; once the node time has passed the prediction is a zero-length patch of the live orbit (drawn as its full ellipse, so it converges onto the plan) followed by the plan starting at the node time. Remaining Δv = planned velocity − the live orbit's velocity at the node time (`remainingManeuverDv`, shared by the navball burn readout, the navball/SAS maneuver direction and the node executor, which therefore resumes a burn already under way correctly). The navball maneuver marker now points along the remaining Δv in the inertial frame at the node, not the node components in the live orbit's frame. An anchored node survives the 600 s expiry while thrusting and is cleared (message "Maneuver complete") once the engines have been quiet for 2 s and the remaining Δv is ≤ max(0.25 m/s, 0.5 % of the node) (cap 2 m/s); an early cut leaves it in place. Precise-gravity (numerical) map paths still re-derive nodes from the live state, as before.

## WP2 editor (2026-10-08, op/wp2)

- **Autostaging over decoupled assemblies:** `autoStage` builds the tree of pieces between decouplers. A stack-decoupled child is a lower (serial) stage: its engines burn, then its decoupler fires in its own stage, then the parent's engines ignite (identical to the old depth stager for serial stacks; a test checks every stock craft without radial decouplers). A radially decoupled child (side latch or surface-mounted decoupler) is parallel: it ignites with its parent and drops in the next stage, so core + boosters light together. Each decoupler fires in the stage that drops its own assembly; engineless side pieces drop just before their parent; fairings open with their assembly's engines (or right after launch on the first stage); chutes fire last. We kept "decoupler, then next engines" as separate stages rather than hot staging: it matches the tuned separation impulses/throttle-cut behaviour (D-feel staging) and the depth stager, so stock designs stage the same.
- **Stock crafts keep the depth stager** (`autoStageByDepth`, Builder option) so their tuned, flight-tested staging is byte-identical; their manual fixes (e.g. Selene's strap-ons) stay.
- **Manual staging survives edits:** the editor tracks `manualStaging` (in undo snapshots). Any stage move/insert/reorder makes staging manual; afterwards new stageable parts are inserted next to the parts the automatic stager would fire them with (same stage), or into a new stage at the matching place in the player's order (`insertIntoStaging`); stages emptied by an edit are compacted. "Reset to automatic staging" (wand) returns to automatic mode. Loaded crafts are manual when their staging differs from the automatic result.
- **Symmetric sets:** picking up any member of a symmetry group lifts the whole set (`detachSubtree(uid, true)`); the held assembly records the set's symmetry, the session shows it as the current symmetry (X still changes it) and restores the player's setting after placement. Placement of held assemblies now re-creates copies (`replicate`): one per parent counterpart, or radial/mirror copies on surfaces. Groups wholly inside a copied subtree stay per copy; every other part is grouped across copies. Occupied counterpart nodes are skipped for re-placed assemblies instead of failing.
- **Alt/Option-click copies** the part's subtree with fresh uids and the same stage numbers (so copies join their originals' stages in manual mode); struts/fuel lines are copied only with both ends.
- **Subassemblies** are stored per device in `localStorage` (`wsp.subassemblies.v1`, 64 max, validated on read: known parts, one tree, valid tweaks). Saved parts are root-relative with no stage numbers and keep the set's symmetry. Drop a held assembly on the drawer (it returns to the craft) or save the selected part's subtree.
- **Offset/rotate tools (2/3), re-root (4), place (1):** gizmo axes are the craft frame; offsets move the part's subtree, rotation pivots on the part's attachment point (surface contact or attach node). Counterparts follow: radial copies through the rotation between the pair, mirror pairs by reflection; Alt drags only the clicked part. Snap (C, default on): 5 cm / 15°, Shift 1 cm / 5°. During a drag only meshes move (pure `transformedParts` preview); the editor commits once on release, one undo step. In the rotate/offset tools W/S/A/D/Q/E turn by 15° or nudge by 5 cm. Attachment metadata is unchanged by offsets (KSP-like).
- **Camera and input:** horizontal pan (Shift+drag, middle drag, horizontal two-finger swipe), F resets it. Wheel zoom is proportional to the delta so trackpads zoom smoothly; pinch (Ctrl+wheel) zooms; Shift+wheel pans vertically. On macOS Ctrl+click is the secondary click (part details) and hints show ⌥/⌫.
- **Safer delete:** Delete/Backspace on the hovered part deletes and shows an Undo toast (single undo, only if nothing changed since). The pre-flight review is hidden until the craft has an engine; its text wraps.
- **Readouts:** a body picker (planets/moons with solid surfaces) sets gravity and surface pressure for the stage list; launch checks always use Earth. Stages show TWR at ignition → burnout and vehicle mass before → after the burn. The first stage reads at the body's surface, later stages in vacuum; airless bodies read vacuum only.
- **Couplers:** five original multi-way couplers (1.25 m → 2/4 × 0.625 m, 2.5 m → 2/3/4 × 1.25 m) appended to the catalogue (existing order unchanged), placed explicitly in structures tiers 1–2. Sockets touch at the axis; the quad's outer sockets sit slightly proud of the stack.
- **Procedural fairings:** shell size per instance in `PartTweaks.fairingHeight/fairingRadius` (`fairingAuto` false stops fitting; manual sizing sets it). The editor fits every auto shell to the parts reached through the fairing's top node after each edit (flare, 58 % cylinder, tangent ogive; radius ≥ catalogue, ≤ 2.5 × ring; rounded to 5 cm / 2 cm so meshes are shared). The simulation (`sim/vessel/fairing.ts`) treats parts whose hull points are inside the shell as shielded: zero exposed areas (no drag, lift, convective heating or radiation) while the fairing part carries the shell's projected areas, acting 40 % up the shell. Shell area beyond the catalogue shell costs 4 kg/m². Absent tweaks use the catalogue shell, so old crafts with fairings now shield what fits inside it.
- **Fairing jettison keeps the payload:** previously jettisoning split off the fairing's whole subtree, throwing away a payload mounted on it. The payload is now re-parented to the part below and only the fairing (ring and shell) separates; a ring-height gap remains between stage and payload (no render-only shell split yet).
- **Undo treats pick-up + place as one action:** the core history still records the held state, but session undo/redo step through it, so Ctrl/⌘+Z after placing a copied or moved set removes it instead of putting it back on the cursor.
- **Merge** (load dialog checkbox) holds another craft as an assembly (root on the cursor, stage numbers dropped so it is staged like new parts). Stock vehicles in the load dialog get rendered thumbnails (idle queue, as saved crafts).
- **Toolbar:** the build-tool group needs ~200 px, so the Parts stat and Actions label hide at ≤ 1800 px and the file/sharing/marker groups move into "More tools" at ≤ 1500 px (was 1200 px).

Stored craft ids stay `'VAB' | 'SPH'` so saves, share codes, localStorage and multiplayer messages are unchanged.
